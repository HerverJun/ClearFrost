## 2. 这套软件到底在做什么

从业务角度看，ClearFrost 是一套**工业视觉检测平台**。它的核心目标是：

- 接收人工触发或 PLC 触发
- 控制工业相机完成取图
- 将图像交给 YOLO 模型进行推理
- 根据目标标签和目标数量判断合格 / 不合格
- 将结果回写给 PLC
- 将结果、图像、日志、统计、历史记录落盘
- 在前端实时显示图像、状态、统计和日志

### 2.1 当前代码体现出的主要功能能力

- **多模型推理**：主模型 + 辅助模型 1 + 辅助模型 2
- **自动回退/切换**：主模型未命中目标时自动尝试辅助模型
- **多任务支持**：检测、分类、分割、姿态、OBB
- **多品牌相机支持**：华睿 / 海康 / Mock / Provider 抽象
- **多协议 PLC 支持**：三菱 MC ASCII、MC Binary、Modbus TCP、西门子 S7、欧姆龙 FINS
- **双 PLC 驱动栈**：HslCommunication + McpX
- **ROI 过滤**：只保留中心点落在 ROI 内的检测框
- **图像追溯**：合格 / 不合格图像分目录保存
- **检测日志**：按日按小时落文本
- **统计看板**：今日统计 + 最近 7 天历史
- **数据库落盘**：SQLite 保存检测记录
- **WebView2 前后端桥接**：C# 与 HTML/JS 双向消息通信
- **工业现场优化**：异步图像保存、日志节流、图像缩放传输、优雅退出、防重复触发

## 4. 入口、启动、退出的完整生命周期

## 4.1 程序入口：`ClearFrost/Program.cs`

`Program.Main()` 做了 5 件非常关键的事：

1. 将工作目录强制切到程序基目录，避免 IDE 启动路径不一致导致找不到文件
2. 在程序目录写 `startup.log`
3. 注册全局异常处理：UI 线程异常 + 非 UI 线程异常
4. 调用 `ApplicationConfiguration.Initialize()` 初始化 WinForms 运行环境
5. 启动主窗体 `Application.Run(new 主窗口())`

### 4.1.1 全局异常处理策略

- `Application_ThreadException(...)`
    - 处理 UI 线程异常
    - 调用 `LogException(...)`
    - 弹窗提示用户错误已记录

- `CurrentDomain_UnhandledException(...)`
    - 处理非 UI 线程异常
    - 同样写日志并提示严重错误

- `LogException(...)`
    - 日志写入 `Logs/crash_yyyyMMdd.log`
    - 记录消息、堆栈、InnerException

### 4.1.2 这段入口代码的工程意义

- 解决“从 VS 启动和双击 exe 启动行为不一致”的问题
- 解决现场闪退后无日志可查的问题
- 将异常收敛到固定目录，便于售后排查

## 4.2 主窗口构造阶段：`ClearFrost/Views/主窗口.cs`

主窗口构造函数不是简单初始化控件，而是整个系统的“装配中心”。

构造函数主要做了这些事：

- `InitializeComponent()` 初始化 WinForms 宿主控件
- 创建 `CameraManager` 并从配置加载相机列表
- 创建 `CameraService`
- 决定当前活动相机句柄 `cam`
- 设置窗口标题、边框与默认最大化
- 创建 `WebUIController`
- 将配置中的 `UseFileBackedWebImageTransport` 和 `IndustrialRenderMode` 注入运行时
- 创建所有服务对象：
    - `PlcService`
    - `DetectionService`
    - `StorageService`
    - `StatisticsService`
    - `SqliteDatabaseService`
    - `ImageSaveQueue`
- 异步初始化数据库
- 注册全量事件 `RegisterEvents()`

### 4.2.1 这里体现出的设计风格

这套系统没有引入完整的 DI 容器，而是采用了**手工装配型服务架构**。优点是：

- 结构直观
- 容易跟踪对象创建来源
- 对工业现场项目更可控

代价是：

- 主窗口承担了较强的 orchestration 角色
- 后续若继续扩展，可能需要进一步解耦

## 4.3 初始化阶段：`主窗口.Init.cs`

初始化不是一次性同步完成，而是分为“窗体加载完成 → WebUI 就绪 → 模型/相机/配置逐步恢复”三层。

### 4.3.1 `主窗口_Load(...)`

窗体加载事件会继续触发异步初始化流程。

### 4.3.2 `InitializeAsync()`

该方法是主初始化中枢，关键动作包括：

- 调用 `WindowHelpers.PreventSleep()` 阻止系统休眠
- 订阅 WebUI `OnAppReady` 事件
- 在前端 Ready 后推送：
    - 相机名称
    - 相机列表
    - 当前配置
    - 今日统计数据
    - 模型列表
- 订阅前端修改置信度 / IoU / 任务类型 / ROI / 密码验证 / 设置保存等事件
- 恢复辅助模型配置与多模型开关
- 触发 YOLO 初始化
- 更新前端状态

### 4.3.3 `InitModelList()`

- 确保 `ONNX` 目录存在
- 扫描所有 `.onnx` 模型文件
- 将文件名列表通过 `SendModelList(...)` 推到前端

### 4.3.4 `InitDirectories()`

- 确保 `Images` / `Logs` / `System` 目录存在

### 4.3.5 `StartCleanupTask()`

- 后台任务循环
- 每 24 小时调用一次 `_storageService.CleanOldData(30)`
- 默认保留 30 天追溯数据

## 4.4 退出阶段：`主窗口.Init.cs`

退出逻辑是当前代码里一个非常成熟的工程化点。

### 4.4.1 `OnFormClosingHandler(...)`

- 拦截关闭请求
- 避免重复进入退出流程
- 对系统关机、任务管理器关闭、用户点关闭按钮等场景统一走优雅退出

### 4.4.2 `BeginAppShutdown(string source)`

这是退出主控方法，核心动作：

- 用 `_shutdownState` 防重复进入
- 写“软件关闭”启动日志
- 置 `停止 = true`
- 取消后台任务 `CancellationTokenSource`
- 停止 PLC 监控
- 恢复休眠策略
- 保存统计数据
- 前端提示“正在安全退出”
- 启动后台清理任务 `ShutdownCleanupCore(...)`
- 启动超时监控 `MonitorShutdownAsync(...)`

### 4.4.3 `ShutdownCleanupCore(string source)`

后台清理动作包括：

- 保存配置
- 释放相机资源
- 销毁 `CameraManager`
- 断开 PLC
- 释放 `ImageSaveQueue`

### 4.4.4 `MonitorShutdownAsync(string source)`

- 等待清理任务完成
- 超时时间是 `_shutdownTimeout = 5s`
- 如果超时，写“关闭超时强退”日志并 `Environment.Exit(0)`
- 如果正常结束，则走 `RequestGracefulExit(...)`

### 4.4.5 退出机制的价值

- 避免现场关闭软件时相机句柄未释放
- 避免 PLC 监听残留
- 避免保存队列中的图像丢失
- 避免统计数据来不及写盘

## 5. 核心业务链路：从触发到结果落地

## 5.1 总体链路图

```text
人工点击 / PLC触发
    ↓
主窗口事件分发
    ↓
CameraService.CaptureFrame()
    ↓
DetectionService.DetectAsync()
    ↓
MultiModelManager / YoloDetector 推理
    ↓
ROI过滤 + 合格判定
    ↓
写PLC结果 + 更新统计 + 存图 + 写数据库
    ↓
WebUIController 推送前端画面、日志、统计、指标
```

## 5.2 PLC 半自动触发链路

### 5.2.1 触发起点

- `PlcService.StartMonitoring(...)` 启动监控循环
- `MonitoringLoop(...)` 定时轮询触发地址
- 当读到值为 `1`：
    - 先自动复位写 `0`
    - 再进入 2 秒防抖窗口判断
    - 延迟 `PlcTriggerDelayMs`
    - 触发 `TriggerReceived`

### 5.2.2 主窗口响应

在 `RegisterEvents()` 里：

- `TriggerReceived` 触发后
- 前端闪烁 PLC 触发指示灯
- 调用 `btnCapture_LogicAsync("PLC半自动")`

## 5.3 手动检测链路：`btnCapture_LogicAsync(...)`

这是整套软件最关键的业务方法之一，建议每位同事认真阅读。

### 5.3.1 并发保护

- 使用 `_detectionSemaphore.WaitAsync(0)` 做零等待抢占
- 如果上一轮检测还没结束，直接提示“检测正在进行中，请稍候”
- 这样能挡住 PLC 快速连发或人工误连点

### 5.3.2 取图策略

优先级如下：

1. 调用 `_cameraService.CaptureFrame(3000)` 触发相机拍照并取实时帧
2. 如果失败，则回退到 `_cameraService.LastFrame`
3. 如果还是没有图，则前端提示“无可用图像进行检测”

### 5.3.3 推理策略

- 调用 `_detectionService.DetectAsync(mat, confidence, iou, targetLabel, targetCount)`
- 该方法内部会自动选择：
    - 多模型模式：`MultiModelManager`
    - 单模型模式：`_yolo`

### 5.3.4 ROI 过滤

- 通过 `FilterResultsByROI(...)`
- ROI 使用归一化矩形 `[x, y, w, h]`
- 判断条件是“检测框中心点是否落在 ROI 内”
- 过滤前后都写 Debug 日志

### 5.3.5 PLC 写结果

- `WriteDetectionResultToPlc(bool isQualified)`
- 根据配置把 `PlcOkValue` 或 `PlcNgValue` 写到 `PlcResultAddress`

### 5.3.6 渲染与保存

- 调 `TryRenderDetectionMat(...)`
- 工业模式优先用纯 `Mat` 路径渲染，减少 `Mat ↔ Bitmap` 转换
- 保存图像时：
    - 不合格图像优先复用已渲染结果
    - 通过 `ImageSaveQueue` 异步写盘

### 5.3.7 统计、数据库、前端

- `_statisticsService.RecordDetection(...)`
- `_databaseService.SaveDetectionRecordAsync(...)`
- `_uiController.SendDetectionFrame(...)`

### 5.3.8 性能画像

方法会对各阶段独立计时：

- 取图耗时
- 推理耗时
- ROI 过滤耗时
- PLC 写入耗时
- 前端渲染耗时
- 图像入队耗时
- 数据库写入耗时

最后用 `WritePerformanceProfileLog(...)` 写详细性能日志。

## 5.4 合格判定逻辑

当前系统实际有两套判定思想：

### 5.4.1 `DetectionService.PopulateResult(...)` 的默认判定

- 如果配置了 `TargetLabel` 且 `TargetCount > 0`
    - 统计命中目标标签的数量
    - `actualCount == targetCount` 即合格
- 否则
    - “检测结果数量为 0”视为合格

### 5.4.2 `主窗口.PLC.cs` 中的 `EvaluateQualificationByTarget(...)`

它提供了一个基于 ROI 过滤后结果重新判定的辅助逻辑。虽然当前主链路里更多使用 `DetectionService` 结果，但这段代码体现了系统预留的“二次判定”能力。

## 7. 主窗口总控逻辑详解

## 7.1 文件拆分方式

主窗口通过 partial 类拆成多个文件，每个文件聚焦一个职责：

- `主窗口.cs`：构造函数与系统组装
- `主窗口.Fields.cs`：字段、共享状态、路径与通用辅助
- `主窗口.Init.cs`：初始化、事件绑定、退出清理
- `主窗口.Camera.cs`：相机打开与参数下发
- `主窗口.Vision.cs`：YOLO 初始化、检测、ROI、图像保存
- `主窗口.PLC.cs`：PLC 连接、结果回写、手动放行

## 7.2 共享字段：`主窗口.Fields.cs`

这个文件的重点是让你理解整个窗体有哪些“全局态”：

- 服务层对象
- `WebUIController`
- `CameraManager`
- 活动相机句柄 `cam`
- 全局配置 `_appConfig`
- 检测信号量 `_detectionSemaphore`
- 应用退出 CTS `_appShutdownCts`
- 关闭状态 `_shutdownState`
- 当前 ROI `_currentROI`
- 图像、日志、系统目录路径属性

### 7.2.1 `SafeFireAndForget(...)`

这是主窗口里非常重要的异步保护工具：

- 统一承接 fire-and-forget 异步任务
- 捕获未观察异常
- 可以追加自定义错误处理
- 避免异步事件处理把异常“吞到线程池”里

## 7.3 事件绑定：`RegisterEvents()`

`RegisterEvents()` 是整套软件的“神经中枢连线图”。

它完成三大类事件绑定：

### 7.3.1 服务层 → UI

- PLC 连接变化 → 更新前端状态与日志
- PLC 触发事件 → 闪烁指示灯并执行检测
- Detection 完成 → 前端记录检测结果日志
- Detection 模型加载 → 前端日志提示
- Detection 错误 → 前端错误日志
- Statistics 更新 → 更新前端总数 / 合格 / 不合格
- 跨日重置 → 前端提示统计已自动重置

### 7.3.2 WebUI → 主窗口业务

主要包括：

- 打开相机
- 手动检测
- 手动放行
- 打开设置
- 切换模型
- 手动连接 PLC
- 退出/最小化/最大化/拖动窗口

## 9. 检测服务与多模型管理

## 9.1 `ClearFrost/Services/DetectionService.cs`

这是 YOLO 业务层封装的门面类。

### 9.1.1 职责

- 管理主模型加载与切换
- 管理辅助模型加载与卸载
- 对外提供统一 `DetectAsync(...)`
- 统一合格判定
- 提供结果绘制
- 对外暴露当前模型、标签、最后推理指标等信息

### 9.1.2 单模型与多模型双路径设计

内部有两个关键成员：

- `_modelManager`：多模型管理器
- `_yolo`：单模型 YOLO 检测器回退路径

这样带来的好处是：

- 优先走多模型架构
- 如果 `MultiModelManager` 初始化失败，可以回退到单模型模式
- 兼顾新架构和历史兼容

### 9.1.3 关键方法

- `LoadModelAsync(...)`
    - 检查文件存在
    - 初始化 `MultiModelManager`
    - 加载主模型
    - 若失败回退到单模型 `_yolo`

- `ScanAndLoadModelsAsync(...)`
    - 扫描 `ONNX` 目录
    - 记录可用模型列表
    - 默认加载第一份模型

- `SwitchModelAsync(...)`
    - 在当前模型基础上重新装载主模型

- `DetectAsync(Mat ...)` / `DetectAsync(Bitmap ...)`
    - 做模型已加载与输入合法性校验
    - 调 `RunInferenceAsync(...)`
    - 调 `PopulateResult(...)`
    - 触发 `DetectionCompleted`

- `RunInferenceAsync(...)`
    - 如果多模型已加载，则走 `MultiModelManager.InferenceWithFallbackAsync(...)`
    - 否则调用 `_yolo.Inference(...)`

- `PopulateResult(...)`
    - 根据 `TargetLabel` / `TargetCount` 计算合格性
    - 回填 `UsedModelName`、`UsedModelLabels`、`WasFallback`、`ElapsedMs`

- `GenerateResultImage(...)`
    - 调当前检测器绘图
    - 若没有可用检测器则返回原图副本

### 9.1.4 事件

- `DetectionCompleted`
- `ModelLoaded`
- `ErrorOccurred`

## 9.2 `ClearFrost/Core/MultiModelManager.cs`

这是“多模型自动切换”的真正落地实现。

### 9.2.1 管理内容

- 主模型 `_primaryModel`
- 辅助模型 1 `_auxiliary1Model`
- 辅助模型 2 `_auxiliary2Model`
- 每个模型对应的路径
- 回退开关 `EnableFallback`
- 统计数据：
    - `PrimaryHitCount`
    - `Auxiliary1HitCount`
    - `Auxiliary2HitCount`
    - `TotalInferenceCount`
    - `LastUsedModel`

### 9.2.2 自动切换策略

`InferenceWithFallback(...)` 的行为非常重要：

1. 先用主模型推理
2. 如果主模型命中目标标签，则直接返回
3. 如果主模型无结果，或者结果不是目标标签，则尝试辅助模型 1
4. 辅助模型 1 未命中，再尝试辅助模型 2
5. 若所有模型都没真正命中，但中途某个模型有“最好的一次结果”，则返回最佳结果

### 9.2.3 `HasTargetLabelHit(...)`

这段方法决定了“要不要继续切换模型”：

- 如果未配置 `targetLabel`，那么只要有结果就算命中
- 如果配置了 `targetLabel`，必须有检测项的标签名与目标标签匹配才算命中

### 9.2.4 统计意义

`ResetStatistics()`、`PrimaryHitRate` 等属性可以帮助你判断：

- 主模型是否足够稳定
- 辅助模型是否经常参与救场
- 当前模型组合是否合理

## 13.2 `ClearFrost/Services/ImageSaveQueue.cs`

这是 V4 预览版工程优化的重要组件之一。

### 13.2.1 设计目的

- 不让图像写盘阻塞检测主链路
- 限制内存占用
- 当磁盘过慢时优先保住实时检测

### 13.2.2 机制

- 基于有界 `Channel<(Mat Image, string Path)>`
- 默认容量 `64`
- `Enqueue(...)` 时会先 `Clone()` 图像
- 队列满时丢弃最旧项，防止慢盘导致内存堆积
- `ProcessLoopAsync(...)` 单线程后台写 `Cv2.ImWrite(...)`

## 15. 性能与稳定性设计总结

- 工作目录强制修正

- 主窗口拆 partial 按职责分文件
- 硬件层抽象成 `ICamera` / `ICameraProvider` / `IPlcDevice`

## 19. 一句话总结

这套代码的本质不是“一个 YOLO 演示程序”，而是：

> **一套围绕工业现场稳定性、实时性、可追溯性、硬件联动和多模型检测而设计的视觉检测平台。**

真正要掌握它，关键不是记住某个按钮点了会调用哪个方法，而是理解下面这四条主线：

- **总控主线**：主窗口负责 orchestrate 全局服务
- **检测主线**：DetectionService + MultiModelManager + YoloDetector
- **硬件主线**：CameraService / CameraManager / PlcService
- **数据主线**：Storage / Statistics / SQLite / WebUI

当你把这四条线都串起来，这个项目就会从“看起来很大”变成“结构很清楚”。
