## 修复 1：相机切换后采集线程仍使用旧相机引用 **[高]**

### 根因分析
- `CaptureLoop()` 在入口处（L361）缓存 `_cameraManager.ActiveCamera` 到局部变量 `activeCamera`，循环内不再刷新。
- `OnSwitchCamera`（主窗口.Init.cs L716-757）仅关闭旧相机、切换 `ActiveCameraId`，**未调用** `StopCapture()` / `StartCapture()` 重启采集线程。
- 结果：切换相机后采集线程仍持有旧相机句柄，导致无画面、异常或帧数据错乱。

### 修改方案

#### `ClearFrost/Views/主窗口.Init.cs`
- 在 `OnSwitchCamera` 事件处理中，**关闭旧相机前先停止采集，切换后重新启动采集**：
```csharp
// L720 之前插入
_cameraService.StopCapture();

// L734 之后（newCam != null 分支末尾）插入
_cameraService.StartCapture();
```

#### `ClearFrost/Services/CameraService.cs`
- (可选加固) 在 `CaptureLoop()` 每轮循环开头从 `_cameraManager.ActiveCamera` 刷新引用，检测到相机变更时自动退出循环：
```csharp
// L365 while 循环内顶部
var currentCamera = _cameraManager.ActiveCamera;
if (currentCamera != activeCamera)
{
    Debug.WriteLine("[CameraService] 检测到相机切换，退出采集循环");
    break;
}
```

### 风险评估
- **低风险**：Stop/Start 是已有公共方法，变更仅在切换事件中增加调用。

### 验证方式
- 构建通过: `dotnet build ClearFrost.sln -c Debug -p:Platform=x64`
- 单元测试通过: `dotnet test ClearFrost.Tests`
- 手动验证: 连接两台相机 → 在前端切换相机 → 确认新相机预览正常、旧相机无残留画面

## 修复 3：YOLO 推理实例非线程安全 **[中]**

### 根因分析
- `YoloDetector` 的预处理方法（`LetterboxResize`、`LetterboxResizeMat` 等）将 `_scale`、`_padLeft`、`_padTop` 写入**实例字段**。
- 后处理 `RestoreCoordinates()` 读取这些字段进行坐标反算。
- 若多线程同时调用同一个 `YoloDetector` 实例的 `Inference()`，这些字段会互相覆盖。

### 修改方案 — 方案 A（推荐，最小改动）：在 `DetectionService` 层加锁串行化

#### `ClearFrost/Services/DetectionService.cs`
- 新增推理信号量，保证同一 `YoloDetector` 实例不会被并发调用：
```csharp
// 字段新增
private readonly SemaphoreSlim _inferenceLock = new SemaphoreSlim(1, 1);

// RunInferenceAsync 中 _yolo.Inference / _modelManager.InferenceWithFallbackAsync 前后
// 分别加 await _inferenceLock.WaitAsync() 和 finally { _inferenceLock.Release() }
```

> **注意**: 当前 `btnCapture_LogicAsync` 已有 `_detectionSemaphore` 防并发，但手动测试和 PLC 触发可能重入，信号量在此层为二道防线。

### 方案 B（彻底但改动大）：将 `_scale/_padLeft/_padTop` 改为方法局部变量
- 需要重构预处理和后处理方法签名，通过参数传递而非实例字段。改动量大，建议后续版本再做。

### 风险评估
- **方案 A 低风险**：仅增加一把锁，不影响正常单线程路径的性能。

### 验证方式
- 构建 + 测试通过
- 手动验证: 快速连续点击检测按钮 → 日志无坐标异常

## 修复 4：统计服务存在并发数据竞争 **[中]**

### 根因分析
- `RecordDetection()` 内先调用 `CheckAndResetForNewDay()`，再调用 `_detectionStats.AddRecord()`。
- 定时器每 10 分钟也触发 `CheckAndResetForNewDay()`。
- `DetectionStatistics.AddRecord()` 和 `Reset()` 直接操作 `TotalCount`、`QualifiedCount` 等，**无任何锁保护**。
- 并行路径：Timer 线程调用 `Reset()` 清零 → 同时 PLC 触发 `RecordDetection()` → `AddRecord` 增加的计数被 `Reset()` 覆盖。

### 修改方案

#### `ClearFrost/Services/StatisticsService.cs`
- 用 `_statsLock` 对象保护所有对 `_detectionStats` 的读写操作：
```csharp
private readonly object _statsLock = new object();

public void RecordDetection(bool isQualified)
{
    lock (_statsLock)
    {
        CheckAndResetForNewDay_Internal();
        _detectionStats.AddRecord(isQualified, persist: false);
    }
    int pending = Interlocked.Increment(ref _pendingSaveCount);
    if (pending >= SaveBatchSize) FlushPendingStatistics();
    StatisticsUpdated?.Invoke(Current);
}

public bool CheckAndResetForNewDay()
{
    lock (_statsLock) { return CheckAndResetForNewDay_Internal(); }
}

private bool CheckAndResetForNewDay_Internal() { ... }
```

### 风险评估
- **低风险**：`RecordDetection` 执行很快，锁竞争极低。

### 验证方式
- 构建 + 单元测试通过

## 修复 8：`SafeFireAndForget` 的异常可能丢失 **[低]**

### 根因分析
- `ContinueWith(async t => { ... })` 返回 `Task<Task>`，外层 `Task` 不等待内层完成，内层异常丢失。

### 修改方案

#### `ClearFrost/Views/主窗口.Fields.cs`
方案 A：改为同步 `ContinueWith`（可用，但可能导致异步前端通知降级）
```csharp
private void SafeFireAndForget(Task task, string name, Action<Exception>? onError = null)
{
    _ = task.ContinueWith(t =>
    {
        if (t.IsFaulted)
        {
            Exception ex = t.Exception?.InnerException ?? new Exception("Unknown error");
            if (onError != null) onError(ex);
            else Debug.WriteLine($"[SafeFireAndForget] {name} 异常: {ex.Message}");
        }
    }, TaskScheduler.Default);
}
```

方案 B（推荐）：保留 async + 加 `.Unwrap()`，确保内层异常被观测且保留异步前端日志能力。

### 风险评估
- **极低风险**。
